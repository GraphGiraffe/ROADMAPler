# ROADMAPler — правила разработки

- Это отдельное приложение для любых проектов; не добавлять зависимости от PlayRoom.
- Публикуемый корень — только `site/`. Не встраивать данные из `projects/` и `archive/` в сайт.
- Как в PECSoteka: исходники в `public/`, команды в `scripts/`, `site/` генерируется и не коммитится. Локально: `npm start`; сборка: `npm run build` (Node.js 22+). Не редактировать сборку вместо исходников.
- Сохранять исходные прототипы и принятые варианты; текущая история находится в `archive/`.
- Будущий объём и границы модулей: `docs/PRODUCT-PLAN.md`, `docs/ARCHITECTURE.md`.
- Формат проектов версионирован. Импорт/обновление не должны терять данные; отвергать неподдерживаемое до изменения проекта.
- Изменения модели проходят через команды с отменой/повтором; пользовательские строки выводить безопасно.
- Тесты выполняются локально. В GitHub Actions пока только сборка и публикация, без Chromium/тестов.
- Не создавать репозиторий, релиз или деплой без соответствующего запроса владельца.
- `main` — стабильная; `dev` — интеграция. Task → PR `dev` squash; публикация → отдельный PR `dev` → `main` squash. Исключение: первый коммит пустого репозитория. Не force-push.
- Pages только вручную: workflow `Publish Pages`, вход `ref` — точный проверенный SHA `main`. Публиковать только `site/`; после deploy проверять опубликованные байты. Push не является публикацией.
- PWA обновляется по кнопке после сохранения текущего сеанса; не активировать новую версию автоматически поверх редактирования. Кеши ограничены scope приложения; пользовательские проекты не входят в кеш оболочки.
- Меню, выбор значений и ошибки форм рисовать внутри приложения; не использовать `alert`, `confirm`, `prompt` или нативные всплывающие списки для настроек. Сохранять автономность экспортированного HTML.

## Supabase Logs Query — обязательное ограничение расхода

- Разделять Logs Query (объём сканирования), Logs Ingest (приём журналов) и Egress (исходящий трафик). Сокращение HTTP-запросов не устраняет сканирование диагностическими инструментами.
- Сначала локальное воспроизведение, тесты с фикстурами, сохранённые результаты и точечные проверки состояния. Начать с [сохранённого аудита](docs/SUPABASE-LOGS-QUERY-2026-10-31.md) и [предыдущих агрегатов](docs/SUPABASE-USAGE-2026-10-31.md). Не перечитывать облачные журналы после исправления, если поведение можно проверить локально.
- Читать облачные журналы только для конкретного нерешённого вопроса. Перед вызовом записать вопрос, ожидаемый признак, проект, источник/сервис, точные UTC start/end и путь сохранения результата. Начальное окно — 5 минут вокруг сбоя. Расширять только с записанным обоснованием, используя уже полученные результаты; не повторять перекрывающиеся окна без новой причины.
- Только подключение `supabase-roadmapler`, привязанное к `project_ref=klsxfhettffjbnmuxivg`. Проверять привязку по локальной конфигурации/известному URL до вызова; не использовать `supabase-playroom`, другие проекты или неограниченный организационный поиск. Рабочие подключения не отключать.
- Для MCP query_logs явно задавать `iso_timestamp_start` и `iso_timestamp_end`; не полагаться на окно по умолчанию (24 часа). Для Management API/CLI/Studio тоже задавать обе границы времени. Фильтровать проект на уровне подключения/API и источник, сервис/endpoint, статус или известный признак сбоя внутри SQL. Не начинать с всех источников, DISTINCT source или исследования всех полей log_attributes.
- LIMIT ограничивает ответ, но не гарантирует малого сканирования. Маленький COUNT/GROUP BY за сутки тоже может дорого сканировать. Агрегаты не заменяют узкое окно и фильтры; не оценивать стоимость только по размеру ответа.
- Сохранять результат локально в `tmp_files/diagnostics/supabase-logs/` с project_ref, UTC-окном, SQL/фильтрами, временем получения, причиной и доступной метрикой bytes scanned. Повторно использовать его; неизвестные метрики не выдумывать. Сохранять только необходимые обезличенные результаты, без токенов и пользовательских данных; в git — краткий обезличенный итог.
- Запрещены циклический опрос Logs Query, автоматическое чтение журналов в тестах/CI/проверках готовности, повторный запрос после таймаута без проверки доступного сохранённого результата. Чтение документации и точечный SELECT состояния не путать с Logs Query.
- Не подключать Log Drains, платные услуги и дополнительный мониторинг без отдельного поручения. Сохранять полезную обработку ошибок и диагностику безопасности; не менять Auth/RLS ради экономии.
- Оценивать новые приращения счётчика по доступной статистике использования без диагностического сканирования журналов. Накопленный расход не уменьшается; ожидаемую экономию отделять от измеренной.
