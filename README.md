# ROADMAPler

Наработки отдельного приложения для планирования любых проектов: треки, релизы, карточки и backlog. Исходный прототип вырос из роадмапа PlayRoom; данные конкретного проекта отделены от сайта.

## Что открыть

- `public/index.html` — исходник автономного прототипа с пустым проектом. Уже работают карточки с описаниями, треки, релизы, backlog, перенос, отмена/повтор, светлая/тёмная тема, импорт/экспорт JSON и сохранение HTML.
- `projects/playroom.roadmap.json` — отдельный проект PlayRoom: 65 карточек, 12 треков. Его можно импортировать кнопкой «Импорт JSON». В сайт эти данные не встроены.
- `archive/prototypes/` — сохранённые предыдущие HTML с данными PlayRoom; `archive/previews/` — снимки предыдущих версий. Это история разработки, не публикация.

Репозиторий: [GraphGiraffe/ROADMAPler](https://github.com/GraphGiraffe/ROADMAPler). Сайт: [ROADMAPler](https://graphgiraffe.github.io/ROADMAPler/).

GitHub Pages публикует **только `site/`**. Корень, `projects/` и `archive/` не являются веб-дистрибутивом; они сохраняются в репозитории как исходники и история разработки.

Приложение устанавливается как PWA и после первого открытия работает без сети. Проекты переключаются вкладками и сохраняются локально в браузере. Названия проектов, треков, релизов и карточек открывают редактирование по нажатию; настройки находятся в диалогах приложения. В ячейках доски есть кнопки создания карточек, а в самой таблице — добавление и скрытие треков и релизов.

Меню `⋯` содержит установку, проверку обновлений, импорт и экспорт. Смена темы находится справа в шапке. Для PWA нужен HTTPS или localhost; скачанный HTML остаётся автономной копией без установки и внешних ресурсов.

Карточку можно растянуть за правый край на несколько релизов или выбрать начало и конец в её настройках. Клавиши ←/→ на рукоятке изменяют конец диапазона. Пересекающиеся карточки располагаются на разных строках внутри трека. Все изменения поддерживают отмену и повтор.

В настройках релиза и backlog выбирается статус по умолчанию: он применяется при переносе в колонку и подставляется для новой карточки. Цвет и иконка в заголовке показывают это правило. Вариант «Не менять статус» оставляет колонку нейтральной. Диапазоны и правила колонок экспортируются в формате проекта версии 2; файлы версии 1 продолжают импортироваться.

## Структура и локальный запуск

Структура следует PECSoteka; имя папки публикации `site/` сохранено по правилам этого проекта.

| Путь | Назначение |
|---|---|
| `public/` | Исходники статического приложения |
| `scripts/` | Команды сборки |
| `site/` | Генерируемая веб-сборка; не коммитится |
| `docs/` | План продукта, архитектура и формат данных |
| `projects/` | Отдельные импортируемые проекты |
| `archive/` | Прототипы и изображения прошлых вариантов |
| `.github/workflows/` | Ручная публикация Pages |
| `CHANGELOG.md` | История изменений |

Нужен Node.js 22+; для локального HTTP-сервера — Python 3. У публикуемого приложения нет npm-зависимостей времени выполнения; браузерные тесты используют отдельную dev-зависимость `playwright-core`.

```sh
npm start       # http://127.0.0.1:4173, исходники public/
npm run build   # готовый сайт в site/
```

Править нужно `public/`: сборка полностью пересоздаёт `site/` и вычисляет ревизию Service Worker по содержимому исходников. Проверка переносимого формата выделена в `public/app/project-format.js`; основная модель доски и интерфейс пока находятся в `public/index.html`, установка и обновления — в `public/pwa.js`, офлайн-оболочка — в `public/sw.js`. При сохранении автономного HTML модуль формата встраивается в файл. Обновление существующего проекта из JSON сохраняет его облачную привязку и остальные метаданные библиотеки.

## Локальные проверки

```sh
npm test                 # JS-контракт и общие фикстуры, только Node.js
npm ci                   # собственные dev-зависимости по package-lock.json
npm run test:browser     # сборка + Chrome/Chromium: импорт, история, HTML и PWA
npm run test:sql         # те же фикстуры на отдельном PostgreSQL
```

Браузерные тесты используют установленный Chrome/Chromium на Linux. Другой путь можно указать через `CHROME_PATH`; при отсутствии браузера установить тестовый Chromium командой `npx playwright-core install chromium`. SQL-проверка рассчитана на Linux/macOS и требует локальных инструментов PostgreSQL (`initdb`, `pg_ctl`, `psql`, `pg_config`), не запускается от root; путь к инструментам можно задать через `PG_BIN`. Она создаёт временный кластер с отдельным Unix-сокетом и отключённым TCP, не подключаясь к рабочему серверу.

Общие данные контракта — `tests/fixtures/project-format.json`. В GitHub Actions остаются только сборка и публикация: тесты запускаются локально. Подробнее: [TESTING](docs/TESTING.md).

## Данные и обновления

Хранилище проектов — версионированная запись `localStorage`, отдельная для пути приложения. Это промежуточное решение до IndexedDB: объём ограничен квотой браузера. При ошибке записи изменение откатывается, форма остаётся открытой; при обнаруженном изменении сохранённой записи другой вкладкой приложение отказывается от перезаписи. Сравнение значения перед записью не заменяет межвкладочную транзакцию. Неподдерживаемый формат хранилища не изменяется; исходную запись можно скачать целиком кнопкой в сообщении об ошибке для последующего восстановления.

История отмены разделена по проектам и хранится в памяти текущего сеанса. Настройки вида, фильтр, поиск и скрытые строки/колонки сохраняются локально для каждого проекта между обычными запусками web/PWA. Перед явным применением обновления состояние сеанса сохраняется в `sessionStorage` текущей вкладки и восстанавливается после перезагрузки. Открытая форма, незавершённый импорт или ошибка сохранения откладывают обновление. Другие вкладки автоматически не перезагружаются.

Новая версия сначала загружает собственный кеш и ждёт кнопки **Обновить и продолжить**. Кеши и данные других приложений на том же домене не затрагиваются. Установка средствами конкретного телефона зависит от браузера; кнопка показывает доступный способ установки.

Экспортируйте JSON или HTML для резервной копии: очистка данных браузера удаляет локальные проекты. Markdown, архив всех проектов, автоматические резервные копии и миграция в IndexedDB пока не реализованы.

## Интеграции

Подготовлены именованные токены для одного облачного проекта с отдельными правами, сроком и отзывом; секрет выдаётся один раз. Агент может читать и менять проект через API с проверкой версии, используя защищённый файл вместо пароля аккаунта. На Supabase владельца SQL-обновления применены; scoped API проверен реальными чтением/записью проекта, точечными запросами, комментарием и чтением результата. Полная приёмка регистрации и синхронизации двух настоящих устройств остаётся отдельной задачей. [Настройка, API и CLI](docs/INTEGRATIONS.md).

Точечный API карточек, треков и релизов, поиск, комментарии и разница после ревизии описаны в [INTEGRATIONS-COMPACT](docs/INTEGRATIONS-COMPACT.md). Для нового развёртывания нужно применить `server/integration-api.sql` после основных миграций; на сервере владельца этот шаг выполнен. Настройки вида доски сохраняются локально для каждого проекта между запусками web/PWA.

## Git и публикация

Как в PECSoteka: `main` — стабильная ветка, `dev` — интеграция. Изменения проходят через task-ветку и PR в `dev` (squash); публикация — после отдельного PR `dev` → `main` (squash). Первый коммит создаёт исходную историю пустого репозитория.

Публикация запускается вручную: Actions → **Publish Pages** → Run workflow на `main`, поле `ref` — точный проверенный SHA коммита `main`. Workflow выполняет `npm run build` и загружает только `site/` без установки зависимостей. На push и PR автоматических запусков нет; тестов и Chromium в Actions нет.

После завершения проверить успешный deploy и совпадение опубликованного `index.html` со сборкой из `public/index.html` выбранного коммита. Push сам по себе сайт не обновляет.
