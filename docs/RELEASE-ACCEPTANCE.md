# Что проверить владельцу перед завершением релиза

Выпуск `agents-2026-10-28` включает новые формы, плагин и защиту вкладок. После публикации используйте обновлённый сайт/PWA; для локального предпросмотра — `npm start` → `http://127.0.0.1:4173/`. Перед обновлением экспортируйте важный проект и закройте остальные старые вкладки приложения: они ещё не участвуют в новом протоколе единственной записи.

Владелец подтвердил применение SQL и добавление Redirect URL. Пункты 1–2 ниже оставлены как справка для повторной установки; заново выполнять их без необходимости не нужно. Следующий шаг — проверка настоящего письма и смены пароля (пункт 3), затем двух устройств (пункт 4).

## 1. Обновить общий helper интеграций (один раз)

Если ещё не применяли обновление из PR #40:

1. Откройте свой Supabase-проект → SQL Editor → New query.
2. Вставьте целиком **текущий** `server/integrations.sql` (готовая копия: `tmp_files/ROADMAPler-integration-auth-update.sql`) и выполните Run. Ожидается успешное выполнение без строк. Таблицы, токены, проекты и ревизии сохраняются; файл допускает повторное применение. Ранее применённые supabase.sql/integration-api.sql заново менять для этого патча не требуется.
3. Выполните проверку ниже; ожидается **true, false, false**.

```sql
select
  position('integration_authorize' in pg_get_functiondef(
    'public.roadmap_integration_access(uuid,text,bigint,jsonb)'::regprocedure
  )) > 0 as uses_shared_authorizer,
  has_function_privilege('anon',
    'roadmap_private.integration_authorize(uuid,text)', 'execute') as anon_can_call_private,
  has_function_privilege('authenticated',
    'roadmap_private.integration_authorize(uuid,text)', 'execute') as user_can_call_private;
```

Административный ключ или пароль Supabase агенту не нужны. Сами ключи/токены не присылайте.

## 2. Разрешить возврат письма в ROADMAPler

Supabase → Authentication → URL Configuration → Redirect URLs. Проверьте адрес приложения и текущий callback `?recovery=1`.

Для прямой проверки стандартного callback можно добавить точное правило:

```text
https://graphgiraffe.github.io/ROADMAPler/\?recovery=1
```

Обратный слеш перед `?` — экранирование wildcard в правилах Supabase. Если интерфейс вашей панели нормализует такое правило и callback не проходит, используйте ограниченный scope приложения `https://graphgiraffe.github.io/ROADMAPler/**` вместо wildcard на весь домен. Для локальной проверки отдельно разрешите `http://127.0.0.1:4173/**`. Не заменяйте Site URL других приложений на этом же Supabase-проекте.

Это не URL для открытия вручную: приложение само передаёт redirect_to при запросе письма. Стандартный шаблон reset-password должен сохранять штатную ссылку подтверждения Supabase. Собственные PKCE/token_hash-шаблоны и включённая CAPTCHA требуют отдельной интеграции; данный интерфейс использует стандартный implicit recovery flow. [Правила Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls).

## 3. Проверить доставку и смену пароля

1. Используйте тестовый аккаунт с почтой, к которой есть доступ. Меню → Аккаунт → «Забыли пароль?» → отправить письмо. Приложение отвечает нейтрально: «Если аккаунт существует…».
2. Откройте пришедшую ссылку. Должна открыться форма ROADMAPler с правильной почтой. Адресная строка должна очиститься от access_token/refresh_token.
3. Введите новый пароль 12–128 символов и повторите его. Несовпадение должно показать ошибку без записи. После успешного сохранения войдите новым паролем обычным способом; старый пароль больше не должен подходить. Проверьте, что проекты на месте.
4. Откройте уже использованную/устаревшую ссылку повторно: приложение должно показать ошибку, а не менять пароль. Если сеть прервалась при сохранении, сначала проверьте вход новым паролем: запись могла пройти; автоматического повтора нет.
5. На телефоне проверьте ссылку из почты в браузере. Переход email → установленная PWA зависит от ОС; отсутствие автоматического открытия PWA не означает потерю данных. На устройстве должен быть установлен новый выпуск.

Если письмо не пришло: проверьте Spam, Auth logs, разрешённый Redirect URL и настройки Email/SMTP. Встроенная почта Supabase ограничивает отправку адресами участников команды проекта и низким лимитом (по текущей документации — 2 письма/час); для произвольных пользователей нужен собственный SMTP. Не отключайте подтверждение почты ради обхода ограничения. [Официальная настройка SMTP и ограничения](https://supabase.com/docs/guides/auth/auth-smtp).

## 4. Проверить синхронизацию двух устройств и изоляцию аккаунтов

Используйте тестовый проект с парой карточек. Два обычных таба одного браузера — **не** два устройства: новая версия даёт право записи только одному табу. Нужны два браузера/профиля, инкогнито или два устройства с независимым хранилищем.

1. Войдите аккаунтом A на обоих устройствах. Создайте тестовый облачный проект и измените одну карточку. Обновление должно появиться на втором устройстве.
2. На первом отключите сеть и измените карточку; на втором измените её иначе. Верните сеть первому. Должно появиться явное разрешение конфликта; вариант «Сохранить обе» должен сохранить обе версии без затирания.
3. Откройте третий независимый профиль и войдите аккаунтом B. Проект A не должен появиться. Не передавайте B токен A: capability-токен отдельно разрешает доступ к своему проекту независимо от входа аккаунта.
4. Перезапустите web/PWA и проверьте проекты и настройки вида. В одном браузере откройте второй таб: он показывает замок/режим просмотра. После закрытия владельца и перезагрузки устаревшего таба запись снова должна работать.

## 5. Проверить токен и плагин

После применения SQL и публикации/в локальном предпросмотре:

1. В Интеграциях скачайте ZIP плагина, проверьте версию/размер/SHA-256 через manifest API. Файл подключения скачивается отдельно и хранится вне репозитория с правами 600.
2. Подключите пакет штатным способом вашего клиента или отдельно MCP по `agent-plugin/README.md`. Убедитесь, что видны три скилла и 18 инструментов, затем вызовите безопасное чтение проекта. Полный импорт ZIP зависит от версии клиента и ещё требует этой приёмки; запуск MCP из чистой распаковки проверен локально.
3. На отдельном тестовом проекте выдайте read-only токен: чтение должно пройти, изменение — завершиться 403. Затем выдайте read/write токен, измените тестовую карточку с текущей ревизией; старая ревизия должна дать 409, сохранив результат первой записи.
4. Отзовите токен через интерфейс: следующий запрос должен дать 401. Не используйте настоящий рабочий проект для проверки удаления.

Критерии готовности: сценарии 1–4 выше выполнены, реальные ошибки записаны без секретов; статусы «Проверить» на доске можно закрыть по фактическому результату. Проверка личного GitHub отдельно требует вашего приватного тестового репозитория и ограниченного Contents-токена; она не выполняется через Supabase. Проверить шифрование, неверный ключ и открытие на втором устройстве; ключ нельзя восстановить по зашифрованному файлу.

Что сообщить после проверки: какие пункты прошли, где остановились, текст/код ошибки и браузер/ОС. Достаточно этих результатов; ссылки с токенами и полный credentials-файл не отправляйте.

## Отдельно: личный GitHub

Эта проверка не требует Supabase и остаётся за владельцем приватного хранилища:

1. Подготовьте отдельный приватный тестовый репозиторий и ограниченный fine-grained токен с Contents read/write только к нему.
2. В ROADMAPler выберите «Мой GitHub», задайте репозиторий/ветку/токен, включите шифрование и отдельный ключ минимум 12 символов; отправьте только тестовый проект.
3. Проверьте файл в репозитории: данные должны иметь формат roadmap-encrypted, а названия/описания тестовых карточек не должны читаться открытым текстом.
4. На другом устройстве подключите тот же репозиторий и ключ: проект должен восстановиться. Неверный ключ должен дать ошибку без изменения файла. Затем правильный ключ должен снова открыть проект.
5. Проверьте отзыв GitHub-токена и сохранность локальной копии. Не отправляйте токен и ключ шифрования в чат; потерянный ключ приложение не восстанавливает.
