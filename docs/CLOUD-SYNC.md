# Синхронизация ROADMAPler

Релиз в разработке. Подготовлены два независимых адаптера: обычный аккаунт через Supabase (вариант по умолчанию) и личный приватный репозиторий GitHub. GitHub Pages продолжает обслуживать только приложение. 27.10.2026 подключён Supabase-проект владельца `klsxfhettffjbnmuxivg`, публичный ключ добавлен в конфигурацию. Реальная связь из Chrome, CORS и запрет анонимного доступа проверены. Проверка авторизованных пользователей и синхронизации ещё ожидает тестовых аккаунтов; это не завершённая приёмка сервиса.

## Локальные и облачные проекты

Без подключения аккаунта приложение работает локально и не делает запросов к провайдерам. Подключение не отправляет существующие локальные проекты: режим каждого проекта выбирается отдельно через настройки → «Синхронизация…».

Облачный проект сначала сохраняется на устройстве. Пока связи нет, его данные и базовая версия остаются в библиотеке проектов. После подключения сравниваются локальное состояние, базовая копия и облачная версия. Неизменившиеся проекты не скачиваются повторно. Проверка выполняется примерно раз в 15 секунд, после локальных изменений, восстановления сети и возврата в приложение; ошибки увеличивают интервал повторов до двух минут. Скрытая вкладка не опрашивает сервер.

Перевод в локальный режим отключает обмен для проекта, оставляя уже созданную облачную копию. Повторное включение того же подключения проверяет изменения обеих сторон. Перед привязкой другого аккаунта проект нужно перевести в локальный режим. Отключение аккаунта прекращает обмен; доступные на устройстве копии остаются.

Удаление облачного проекта подтверждается как удаление на устройстве и в облаке. Без сети намерение хранится в `cloudDeletions`. Удаление проверяет версию; конкурентные изменения требуют решения пользователя. В облаке остаётся отметка удаления, которая защищает от случайного восстановления устаревшим устройством. Кнопка восстановления на устройстве отменяет ещё не отправленное удаление; при уже применённом удалении может понадобиться разрешить конфликт.

## Конфликты и версии

При разных изменениях на двух устройствах автоматического затирания нет. «Сохранить обе» принимает облачное состояние в исходный проект и создаёт отдельную локальную копию собственного. «Отправить мою» сначала сохраняет облачное состояние отдельной локальной копией, затем выполняет запись с проверкой актуальной версии. Если версия снова изменилась, запись отклоняется.

В настройках проекта доступны версии облака. Восстановление версии меняет локальный проект через историю отмены; последующая синхронизация создаёт новую облачную версию. Перезапись истории Git и force-push не используются.

## Личный GitHub

1. Создать отдельный **приватный** репозиторий для данных и выбрать ветку. Репозиторий исходников приложения для личных проектов не используется.
2. Создать fine-grained personal access token с доступом **только к этому репозиторию**, разрешение Contents: read/write. Токен вводится в приложении, не в чате, исходниках или JSON проекта.
3. Меню → «Аккаунт» → «Мой GitHub»: указать `владелец/репозиторий`, ветку и токен.
4. По умолчанию включено шифрование: задать отдельный ключ минимум из 12 символов. На другом устройстве нужен тот же ключ.
5. Включить облачный режим выбранного проекта.

Файлы находятся в `roadmapler/projects/<uuid>.json`. Обновление использует SHA файла; конфликтующие записи отклоняются GitHub. Просмотр версий запрашивает последние 20 коммитов файла. Git сохраняет и более раннюю историю: ограничение просмотра не удаляет её и не уменьшает размер репозитория.

Шифрование: WebCrypto, AES-GCM 256, случайные IV и соль для каждой записи, PBKDF2-SHA-256, 600000 итераций. В репозиторий не передаются открытые названия, карточки или ключ шифрования. Видны идентификаторы файлов, факт удаления, размеры и история обращений. Это шифрование удалённой копии; локальная библиотека браузера и обычный JSON/HTML-экспорт содержат открытые данные.

Ключ шифрования хранится только в памяти и запрашивается после повторного открытия. Без него восстановление невозможно. Токен сохраняется в sessionStorage либо, при явной галочке «Запомнить подключение», в localStorage. Пароль входа Supabase и ключ шифрования туда не записываются. Такой способ хранения токена зависит от защиты устройства и страницы от постороннего кода; защищённого системного хранилища PWA здесь нет. Ключи разделены по пути приложения для именования, но страницы одного origin имеют общие права доступа к browser storage.

Истечение или отзыв токена останавливает обмен до повторного подключения. Токены никогда не записываются в экспортируемые проекты и HTML.

## Обычный аккаунт через Supabase

Подготовлено для Supabase Auth (почта/пароль), PostgreSQL и PostgREST. Собственный постоянно работающий Node-сервер не нужен.

Настройка владельцем:

1. Создать проект Supabase. В SQL Editor применить `server/supabase.sql`. Скрипт можно применить повторно.
2. В Authentication включить вход по почте/паролю, настроить Site URL и разрешённые redirect URL на адрес приложения.
3. Для публичной регистрации и подтверждения почты подключить собственный SMTP. Встроенная тестовая отправка Supabase ограничена адресами членов команды проекта.
4. В `public/cloud/config.js` указать `supabaseUrl` и публичный `supabaseKey` (`sb_publishable_…` либо legacy anon JWT). **Никогда не использовать secret/service_role key.** Сборка отвергает заведомо неподходящие ключи до копирования в `site/`.
5. Проверить реальную регистрацию, письмо подтверждения, вход двух пользователей, доступ с двух устройств, конфликт, офлайн-очередь и восстановление версий. Только затем публиковать стабильный релиз.

Пользователь не вводит URL базы или административные ключи. Публичный ключ приложения не даёт доступ к чужим данным: чтение ограничено Row Level Security по `auth.uid()`, запись — отдельной функцией с проверкой владельца и ожидаемой версии. Прямое изменение таблиц клиентом запрещено. Сервисный ключ нельзя выдавать браузеру, поскольку он обходит RLS.

Облачные данные Supabase в этой реализации **не зашифрованы ключом пользователя в браузере**. RLS разделяет доступ пользователей, но администратор сервера имеет доступ к содержимому. Сквозное шифрование обычного режима — отдельное возможное расширение, его нельзя подразумевать из наличия HTTPS или шифрования дисков провайдера.

Начальные ограничения схемы: 1 МиБ на проект, 50 записей проектов на аккаунт (включая отметки удаления), 20 версий каждого проекта и около 10 МиБ данных истории аккаунта. Значения меняются владельцем в SQL; они не заменяют общую квоту Supabase. Восстановление пароля в интерфейсе ROADMAPler пока не реализовано; для публичного запуска нужно определить этот сценарий и проверить настройки почты.

### Бесплатный тариф: проверено 27.10.2026

По официальным страницам: 500 МБ базы на проект Supabase, 50000 активных пользователей в месяц, 5 ГБ исходящего трафика в месяц, отдельно 5 ГБ кешированного трафика, 1 ГБ файлового хранилища и два активных проекта Supabase. Это лимит инфраструктурных проектов, а не числа пользовательских роадмапов. API-запросы заявлены без отдельного количественного лимита, но трафик и ресурсы ограничены.

Проект Free может быть приостановлен после семи дней низкой активности; автоматические бэкапы в тариф не включены. Файловое хранилище и кешированный трафик не увеличивают квоту обычных SQL-запросов базы. Для ROADMAPler реальный расход будут определять размеры проектов, число устройств и число версий, а не только количество аккаунтов. Оценка вместимости без измерений была бы условной.

## Границы хранения и обновления

В метаданных локальной библиотеки сохраняются привязка проекта к провайдеру/аккаунту, удалённый ID, базовая версия, базовая копия и ожидающие удаления. Формат переносимого проекта остаётся версии 2: привязка и токены не попадают в него. Старый экспорт пользователя сохранён без изменений в `archive/roadmaps/`; актуальная карта разработки — в `projects/ROADMAPler.roadmap.json`. Эти каталоги не входят в сайт.

Service Worker кеширует только оболочку, включая модули облачного интерфейса; ответы облака в него не входят. На время применения PWA-обновления обмен приостанавливается, чтобы снимок сеанса не устарел в процессе переключения версии. При ошибке подготовки или отмене ожидания обмен возобновляется.

## Выполненные локальные проверки

- Отдельный PostgreSQL 18: повторное применение SQL, RLS двух пользователей, запрет анонимного чтения и прямой записи, CAS, неподдерживаемые данные, ротация 20 версий, отметка удаления и восстановление.
- Google Chrome, два изолированных профиля с имитацией GitHub API: локальная изоляция, настоящее WebCrypto-шифрование, загрузка на втором устройстве, офлайн-редактирование с перезагрузкой, конфликт и обе копии, история, отключение проекта без удаления облака, очередь удаления и восстановление уже удалённого облачного проекта с разрешением конфликта.
- Chrome с имитацией Supabase API: вход, запись с версией, разные аккаунты, обновление сеанса, снимок PWA, автономный HTML без токенов и внешних облачных модулей.
- `npm run build`, `node --check` модулей, `git diff --check`.

Имитация API проверяет клиентский протокол, но не доказывает совместимость с реально настроенным сервисом. На предоставленном Supabase проверены HTTP 200 для настроек Auth, включённый вход по почте, обязательное подтверждение почты, CORS и HTTP 401 для анонимного чтения обеих таблиц и вызова функции записи. Авторизованная синхронизация на этом сервере, настоящий GitHub-токен, SMTP и физический телефон пока не проверены. Платные ресурсы и новые репозитории не создавались; новый релиз не опубликован.
