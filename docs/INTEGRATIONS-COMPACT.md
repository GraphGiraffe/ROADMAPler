# Точечный API интеграций

Дополнение к [подключению интеграций](INTEGRATIONS.md). Новые RPC нужно установить в Supabase: после существующих `server/supabase.sql` и `server/integrations.sql` выполнить `server/integration-api.sql`. Миграция добавляет функции, сохраняет данные и допускает повторное применение. До её применения новые команды не работают; прежний API остаётся совместимым. Готовый объединённый файл для SQL Editor: `tmp_files/ROADMAPler-api-update.sql`.

Все запросы — POST с прежними заголовками `apikey`, `X-ROADMAPler-Token`, `Content-Type: application/json`. Секрет по-прежнему находится в отдельном защищённом файле подключения. Права чтения/изменения, выбранный проект, срок и отзыв проверяются сервером. Для удаления самого проекта требуется отдельное разрешение; удаление карточки, трека или релиза относится к изменению проекта.

Каждый ответ содержит `id` облачного проекта, его текущую `revision`, `deleted`, `updated_at`. Новая ревизия общая для UI и всех API. Любое изменение требует `p_expected`/`--expected`, равной последней прочитанной ревизии. HTTP 409 означает конфликт: прочитать актуальное состояние, согласовать изменения, затем отправить новый запрос. CLI не повторяет записи автоматически. Повтор добавления комментария со старой ревизией также отклоняется, поэтому сетевой повтор не дописывает его дважды.

## Карточки

RPC: `/rest/v1/rpc/roadmap_integration_cards`.

| Параметр | Назначение |
| --- | --- |
| `p_project_id` | UUID облачного проекта, обязателен |
| `p_action` | `search` (по умолчанию), `get`, `create`, `update`, `comment`, `delete` |
| `p_task_id` | ID карточки, обязателен кроме поиска; 1–200 символов |
| `p_expected` | Положительная ожидаемая ревизия для изменения |
| `p_patch` | Объект полей для create/update; `{ "text": "…" }` для comment |
| `p_query` | Необязательная строка поиска до 1000 символов |
| `p_track`, `p_release`, `p_status` | Необязательные точные фильтры поиска |
| `p_limit`, `p_offset` | Размер страницы 1–100 (по умолчанию 50), смещение 0–100000 (по умолчанию 0) |

Поиск не учитывает регистр, проверяет ID, название, описание, комментарий и условие готовности. `%` и `_` — обычные символы. Фильтр релиза включает карточки, чей диапазон пересекает этот релиз; `backlog` выбирает только backlog. Порядок результатов соответствует доске. Поиск возвращает `tasks`, `total`, `limit`, `offset`; чтение/запись — одну `task`, удаление — `removed_task_id`. Полный проект не передаётся.

В patch разрешены `title` (1–180 символов), `description` (до 12000), `accept` (до 6000), `comment` (до 1000), `track`, `release`, `releaseEnd`, `status`. Значения — строки; `releaseEnd: null` снимает диапазон. Неизвестные поля и изменение ID отвергаются. Существующие дополнительные данные карточки сохраняются. Диапазон переводит формат проекта в версию 2. Перенос через API сохраняет статус; если его нужно изменить, передайте `status` явно.

При создании нужны ID и обязательные поля `title`, `description`, `track`, `release`, `status`. Новый ID выбирает клиент; существующий ID даёт 409. Ссылки, статусы, диапазоны, размер проекта и квоты проверяются общим серверным валидатором. Patch ограничен 64 КиБ.

`comment` дописывает текст в существующее поле `comment` через пустую строку. Это тот же комментарий, который виден в редакторе; отдельной ленты сообщений нет. Итоговый предел — 1000 символов. Пустое дополнение или превышение предела отклоняются целиком.

Пример точечного изменения:

```json
{
  "p_project_id": "UUID",
  "p_action": "update",
  "p_task_id": "task-id",
  "p_expected": 12,
  "p_patch": { "status": "done", "comment": "Проверено" }
}
```

CLI:

```sh
node scripts/integration-client.mjs search --query "документация" --release release-id --limit 20
node scripts/integration-client.mjs get-card --task task-id
node scripts/integration-client.mjs update-card --task task-id --file /tmp/card-fields.json --expected 12
node scripts/integration-client.mjs create-card --task new-task-id --file /tmp/new-card.json --expected 13
node scripts/integration-client.mjs comment --task task-id --file /tmp/comment.txt --expected 14
node scripts/integration-client.mjs delete-card --task task-id --expected 15 --confirm-delete task-id
```

Файлы create/update содержат только объект полей; файл comment — обычный UTF-8 текст. `--out` сохраняет компактный ответ в новый файл с закрытыми правами. Ревизии в примерах условные: используйте значение предыдущего успешного ответа, а не предполагаемый номер.

## Треки и релизы

RPC: `/rest/v1/rpc/roadmap_integration_structure`.

Общие параметры: `p_project_id`, `p_expected`, `p_query`, `p_limit`, `p_offset`. Дополнительно:

| Параметр | Назначение |
| --- | --- |
| `p_kind` | `tracks` или `releases` |
| `p_action` | `search`, `get`, `create`, `update`, `delete` |
| `p_entity_id` | ID, обязателен кроме поиска |
| `p_patch` | Поля создания/изменения |
| `p_position` | Позиция с нуля; при создании по умолчанию конец, при изменении прежняя |
| `p_cards` | `delete` или `move`; обязательно при удалении сущности с карточками |
| `p_target_track` | Существующий трек назначения для переноса |
| `p_target_release` | Существующий релиз назначения или `backlog` |

Поля трека: `title` (1–100), `subtitle` (до 300). Поля релиза: `title` (1–100), `note` (до 200), `defaultStatus` (статус или пустая строка; `null` снимает правило). Статус колонки включает формат 2. Неизвестные поля отвергаются, дополнительные существующие данные сохраняются. Поиск проверяет ID, название и описание. Результат — `tracks`/`releases` и пагинация; get/create/update возвращает `track`/`release`. Изменение порядка можно отправлять без patch, только с позицией и ревизией; границы диапазонов нормализуются по новому порядку релизов.

При удалении трека с переносом обязателен другой `p_target_track`; без `p_target_release` карточки сохраняют текущие релизы и диапазоны. При удалении релиза с переносом обязателен `p_target_release`; без `p_target_track` сохраняются текущие треки. Учитываются все карточки, пересекающие релиз: переносятся/удаляются целиком. Выбор конкретного релиза назначения снимает диапазон. Статусы сохраняются. Ответ содержит `removed_entity_id` и `affected_tasks`. Вся операция атомарна и проверяет одну ревизию.

Для нового трека в backlog сначала создайте трек точечным запросом, затем используйте его ID и полученную ревизию в удалении с переносом в backlog. Последний трек через API удалить нельзя: сначала создайте замену. Это сохраняет обязательную структуру проекта и не создаёт неявных сущностей. Зарезервированные `backlog` и `add-release` нельзя создавать/редактировать как релизы; правило backlog остаётся частью полного проекта.

```sh
node scripts/integration-client.mjs search-tracks --query "разработка"
node scripts/integration-client.mjs get-release --id release-id
node scripts/integration-client.mjs create-track --id new-track --file /tmp/track.json --expected 16
node scripts/integration-client.mjs update-release --id release-id --file /tmp/release.json --position 0 --expected 17
node scripts/integration-client.mjs delete-release --id release-id --cards move --target-track new-track --target-release backlog --expected 18 --confirm-delete release-id
node scripts/integration-client.mjs delete-track --id old-track --cards delete --expected 19 --confirm-delete old-track
```

## Изменения после ревизии

RPC: `/rest/v1/rpc/roadmap_integration_changes`; тело `{ "p_project_id": "UUID", "p_since": 12 }`.

CLI: `node scripts/integration-client.mjs changes --since 12`.

Ответ содержит `from_revision`, текущую `revision`, `reset_required` и `changes`. Это совокупная разница между указанной ревизией и снимком текущего состояния, включая записи обычного UI и прежнего API; это не журнал отдельных действий.

- `changes.fields` — новые/изменённые корневые поля проекта, кроме `tracks`, `releases`, `tasks`; применить заменой целого значения поля. Включает `sources` и любые дополнительные метаданные.
- `changes.removed_fields` — удалённые корневые поля.
- Для изменённых коллекций `tracks`, `releases`, `tasks`: `upsert` — целые добавленные/изменённые сущности по ID; `removed` — удалённые ID; `order` — полный итоговый порядок ID этой коллекции. Сначала удалить, затем заменить/добавить по ID, затем восстановить порядок. Неизменённых коллекций в changes нет.
- Если ревизия уже текущая, `changes` равен `{}`.
- Если базовый снимок отсутствует (хранится 20 последних версий), `p_since=0` либо исходная ревизия — отметка удаления, сервер возвращает `reset_required: true`, `changes: null`. Требуется один обычный `read`; нельзя применять частичную разницу.
- Удалённый проект возвращает `deleted: true`, `changes: null`; локальный снимок следует считать удалённым. После восстановления с удалённой базовой ревизии потребуется полный read.
- Будущая или отрицательная ревизия — 400. Чтение изменений требует права чтения, а не изменения.

Страницы поиска не являются сохранённым снимком: если `revision` между страницами изменилась, перечитайте страницы. Для точной локальной копии используйте read + changes.

## Проверки и развёртывание

Новые SQL-функции и CLI проверяются локально на отдельном PostgreSQL, включая конкурентные запросы, права, конфликты и точное восстановление JSON из разницы. Проверка локального HTTP-слоя не означает, что миграция уже применена на действующем Supabase. После применения владельцем нужно проверить RPC на сервере; административный ключ агенту не требуется.
