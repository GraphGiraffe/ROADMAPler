# Аудит Logs Query · 31.10.2026

Владелец сообщил 16,345 ГБ Logs Query при 0,039 ГБ Logs Ingest. Это разные метрики: Logs Query учитывает сканирование через Studio, Management API, CLI и другие интерфейсы, а не размер возвращённого ответа. Egress учитывается отдельно. [Документация Supabase](https://supabase.com/docs/guides/platform/manage-your-usage/logs-query) рекомендует узкие периоды, фильтры внутри запроса и отсутствие scripted polling: одинаковый запрос сканирует данные снова.

## Подтверждённые причины

В сохранённой истории этого чата найдены **7 фактических вызовов** `supabase_roadmapler.query_logs` за 30.10.2026 17:51:29–17:54:00 UTC. Все без явных start/end, то есть инструмент использовал скользящие последние 24 часа. Это моя предыдущая диагностика HTTP-расхода, не фоновая работа ROADMAPler:

| Запросы | Область сканирования |
| --- | --- |
| 1 | Все источники, COUNT по source |
| 2 | edge_logs: ключи log_attributes и частые API пути/статусы |
| 1 | edge_logs + auth_logs: поиск имён полей |
| 3 | edge_logs: один endpoint roadmap_projects, разные агрегаты select/Referer/часов |

Окна почти полностью перекрывались; результаты ограничивались LIMIT 8–18, но это не ограничивало сканирование исходного периода. Точных повторов SQL среди этих семи нет, повторное чтение практически одного периода есть. Первые широкие запросы и исследование схемы атрибутов были избыточны для конкретного вопроса. Краткие результаты уже сохранены в [аудите HTTP-расхода](SUPABASE-USAGE-2026-10-31.md), поэтому перечитывать их не нужно.

Эти семь вызовов подтверждены, однако число bytes scanned по каждому в доступной истории отсутствует. Нельзя приписать им весь счётчик 16,345 ГБ или вычислить точную экономию. Другие чаты, ручные сессии Studio и сторонние клиенты не представлены полной историей в этом аудите. Указанные владельцем объёмы не проверялись новым облачным запросом.

## Локальный код и подключения

Поиск по public/, scripts/, server/, tests/ и .github/ не обнаружил вызовов query_logs/get_logs, Logs Query/Management analytics endpoints или периодического чтения журналов. Приложение опрашивает Data API для синхронизации, что порождает HTTP Logs Ingest/Egress, но само не выполняет Logs Query. Автоматические тесты обращаются к фикстурам и локальным серверам. Следовательно, менять интервал синхронизации ради Logs Query оснований нет.

Локальная конфигурация MCP проверена без вывода секретов: `supabase-roadmapler` имеет URL `https://mcp.supabase.com/mcp?project_ref=klsxfhettffjbnmuxivg&features=docs%2Caccount%2Cdatabase%2Cdebugging%2Cdevelopment%2Cfunctions%2Cbranching%2Cstorage`. Исторические вызовы использовали именно это подключение. Отдельный `supabase-playroom` привязан к другому проекту; в семи проверенных вызовах он не использовался. Подключения и credentials не менялись. Проверенная конфигурация сама не задаёт расписания чтения логов; глобальное отсутствие сторонних читателей этим не доказано.
